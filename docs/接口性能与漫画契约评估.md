# NAS 接口性能与漫画契约评估

评估日期：2026-09-24。依据当前 NAS、Android 代码和 `NAS漫画接口契约.md`、`NAS小说接口契约.md` 静态检查；没有在实际 NAS 上测量寻道、吞吐、功耗或硬盘唤醒次数。漫画接口尚未实现，`server-info` 明确声明能力关闭。用户已明确漫画首版需要 PDF 与断点续传，不能按只有 ZIP/CBZ 的范围上线。

## 现有接口的磁盘行为

| 接口/操作 | 当前访问 | 评估 |
|---|---|---|
| `/health`、影片/演员/分类/历史列表与详情 | 内存或 SQLite；不遍历影片目录 | 正常轮询不会扫描媒体盘。SQLite、WAL 和日志所在的 `/data` 会有读写。 |
| `/api/v1/server-info` | 查询内存状态；配置 MDCNG 后检查其挂载文件 | 已增加 30 秒单飞缓存，减少客户端频繁刷新造成的文件打开。可用性变化最长延迟约 30 秒反映。 |
| 海报、轮播图、托管图片 GET/HEAD | `/data/artwork` 文件；当前 `no-store` | 客户端重复请求会重传字节。建议给鉴权图片加 `private, no-cache` 和弱 ETag/条件 GET；资源替换时须可靠失效。SSD 上的 `/data` 可减轻这类读取。 |
| 播放会话与 Range 流 | 每次会话/Range 校验媒体路径和长度，流只读取请求范围 | 这是实际播放所需的机械盘读取。客户端频繁发短 Range 会增加寻道；应观察真实播放器模式，再决定是否做顺序预读或限流。不可跳过路径边界校验。 |
| 播放进度 PATCH | 每次正式播放上报更新历史与续播位置，诊断日志也写 `/data` | 高频上报会放大 SQLite/WAL 写入；短期将 `/data` 放 SSD。以后若节流，需保证暂停/结束立即落盘，并保持创建新会话时续播位置可见。 |
| 管理员媒体目录浏览、类别扫描、MDCNG 导入预览 | 浏览目录；扫描递归枚举、逐文件 `stat`，改变文件才用 `ffprobe` | 生产环境启动不自动扫描。重复扫描仍会触发大量元数据 I/O，且当前扫描任务可并发并逐文件更新 SQLite。建议同一目录扫描合并、全局串行，未变化记录不更新 `updated_at`。 |
| 小说列表/详情/下载 | 列表/详情查索引；启动和内容 GET/HEAD 现只检查存在和长度 | 已去掉启动和每次下载前的全文 SHA-256。上传复用、备份和恢复仍保留完整摘要验证；客户端下完后仍须校验 SHA-256。同长度静默损坏不会在普通启动/下载前被发现。 |
| 小说备份/恢复 | 创建备份读取并校验在线正文，复制后再次校验；恢复也完整校验 | 是显式管理任务，不应在播放高峰自动运行。备份内容不能放在机械盘休眠策略未考虑的位置。 |

另外，多个普通 JSON 路由共用无总量上限的 `_readJsonBody`，会把完整请求体拼接后解析。引入漫画会话接口前应按端点设置合理的 JSON 大小限制；现有资料导入接口需要单独核对上限，避免意外拒绝合法大批量操作。

恢复维护状态只等待 HTTP 请求，不等待后台扫描任务。恢复切换数据库前应阻止新扫描并等待当前扫描结束，或让扫描安全取消；否则后台任务可能与 SQLite 关闭/重开交错。这是漫画备份与恢复上线前需要解决的功能问题。

播放流计数目前用于观测，没有并发上限；管理员也可同时发起多个扫描或备份。应为扫描、备份和将来的漫画大文件上传分别设置准入与排队规则，避免多个顺序读写任务叠加成机械盘随机 I/O；播放流上限应按实际 NAS 带宽和用户数量测定，不能随意限制正常家庭并发播放。

## 漫画契约的实现判断

1. **完整首版范围**：按契约分别在列表/详情/Range 下载、完整上传、五个会话接口真正可用后开启 `comics`、`comicUpload`、`comicUploadResume`；用户要求的首版验收还包括管理端替换/删除、真实 ZIP/CBZ/PDF 校验、崩溃恢复和备份排除。当前没有漫画表、存储目录、路由或 Linux PDF 校验器；客户端不能依据评审稿开始调用。
2. **大文件与断点续传**：上传临时文件、对象和隔离区保持同一文件系统。分片顺序追加并 `flush` 后，才提交 SQLite offset 并返回 `204`；进程重启时截断超过已确认 offset 的尾部。单次最多一个大文件写入，分片建议 32 MiB，过小的非末片拒绝。完成时最多再顺序读一遍校验 SHA-256 和格式；列表、查询、下载不重算大文件摘要。相同幂等键的完整上传重试仍可能重新写完整临时文件，因此大文件应优先走会话，建议契约明确大小阈值及客户端策略。
3. **格式验证**：ZIP/CBZ 应基于可靠解析器检查中央目录、签名、路径、重复项、符号链接、加密、条目/解压总量、压缩比，并流式验证必要的数据完整性，禁止将 2 GiB 文件或全部页面载入内存。Android 当前用 `archive` 读取 ZIP，用 `pdfrx`/PDFium 解析 PDF；NAS 的 Dart 服务和 Debian 镜像没有 PDFium/Poppler。PDF 必须增加独立 Linux 解析依赖，限制处理时间与内存，验证页数、加密和截断，不以 `%PDF` 文件头代替解析。
4. **备份与恢复**：现有 `VACUUM INTO` 会复制整份 SQLite。漫画表上线时，仅在 manifest 写 `comicContentIncluded: false` 仍不够；备份的隔离 SQLite 快照必须清空漫画记录、对象引用、配额、会话和幂等状态。恢复旧备份也要清理漫画业务表，不能把原漫画文件误删，更不能留下可见但无法下载的记录。管理端备份文案须明确排除漫画原文件。
5. **SSD 使用**：优先把 `/data`（SQLite/WAL、状态、日志、图片）放 SSD；影片只读挂载和漫画对象留在 HDD。若漫画临时上传放 SSD、正式对象放 HDD，就失去同文件系统原子改名，还会产生跨盘复制；这需要重新设计耐久发布和断电恢复，不能只改挂载。SSD 也不能代替大小、摘要、配额和空间不足检查。
6. **契约需补充的边界**：省略 `fileName` 时，`<标题>-<64 位摘要>.<格式>` 可能超过 256 个 Unicode 标量，应规定截断标题、保留完整摘要和扩展名。应明确多页 PDF 的最大页数、解析超时，以及 ZIP/CBZ 对非图片文件的处理规则，保证 NAS 接受的文件一定能由 Android 当前导入器使用。
7. **下载中的 I/O 错误**：发送 `200/206` 响应头以后，磁盘中途读取失败无法再改成 JSON `503`。服务端应在发送响应头前检查文件并尽量提前打开；中途失败则中断连接并标记对象异常，Android 根据长度和 SHA-256 校验拒绝导入。契约中的 `503 comic_content_unavailable` 只能保证适用于发送响应头之前发现的错误。

## 建议验收

- 用包含 ZIP/CBZ、PDF、图片目录打包 ZIP 的实际文件，在 Android 导入器与 NAS 校验器间做正反例交叉测试。
- 用大文件测试连续分片、丢失响应、重复分片、错 offset、进程重启、断电后尾部截断、完成请求重放和取消；核对 SQLite offset 永不超过已持久化文件长度。
- 在实际 NAS 上分别观察空闲轮询、连续浏览海报、播放 Range、类别扫描、漫画上传/下载和备份的磁盘读取与唤醒。建立基线后再决定缓存大小及进一步节流。
